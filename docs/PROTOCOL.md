# The Ro/Box wire protocol

Implemented twice, once per language, and they must agree byte for byte:

| | |
|---|---|
| firmware | [`src/protocol.py`](../src/protocol.py), [`src/framed.py`](../src/framed.py) |
| website | `src/libs/communication/frames.ts`, `uploader.ts` |
| conformance vectors | [`tests/vectors/frames.json`](../tests/vectors/frames.json), generated by [`tools/gen_vectors.py`](../tools/gen_vectors.py) |

Change one side and the vector tests fail. That is the point: the alternative
is finding out from a board.

## Why it exists

The old protocol put control commands and program text on one unframed
channel, and the firmware compared every received line against a command
table. Two failures follow from that, both measured rather than theorised:

1. **Silent corruption.** A dropped BLE packet turned a line of code into a
   different line of code. Neither end could tell, so the board stored it and
   ran it.
2. **Command injection.** A line of *user code* equal to a command was executed
   instead of stored. The baseline run had a corpus send 122 bytes and the board
   store 49, over a perfect USB link, with no error raised.

Both are the same root cause: payload bytes were being interpreted. Here they
never are.

## Frame layout

```
\x01 SS LL CCCC K : <payload> \n
 |   |  |  |    | |
 |   |  |  |    | +-- separator
 |   |  |  |    +---- kind, one character
 |   |  |  +--------- checksum, 4 hex digits
 |   |  +------------ payload length, 2 hex digits
 |   +--------------- sequence number, 2 hex digits, mod 256
 +------------------- SOH, the resync sentinel
```

The header is a fixed 11 bytes, so a partial frame is detectable immediately
rather than after a parse attempt. Payloads exclude `\x01` and `\n`, which
gives two useful properties: SOH is an unambiguous place to resynchronise after
loss, and one frame is always one line, so the existing line-oriented plumbing
on both sides works unchanged.

Maximum payload is 108 bytes, six BLE chunks including overhead. Longer source
lines are split across `C` frames on character boundaries, never mid-codepoint.

### Kinds

| kind | meaning |
|---|---|
| `D` | program text, ends a line |
| `C` | program text, line continues in the next frame |
| `B` | begin upload; payload is `<lines>,<crc32>` |
| `E` | end upload; payload is `<crc32>` |
| `X` | control command, by name |
| `A` | cumulative acknowledgement, payload `<expected>,<credit>` |
| `N` | negative acknowledgement, same payload shape |
| `R` | device to host message, payload is JSON |

Control and data are distinguished **here**, by the kind field. A `D` frame's
payload is never inspected, so it can spell `x04STARTPROG` and remain data.

### Checksum

The low 16 bits of CRC-32, over the sequence number, length, kind and payload.
Covering the header matters: a corrupted header is how a frame gets misrouted,
and a payload-only checksum would not notice.

CRC-32 rather than a bespoke CRC-16 because `binascii.crc32` is native C on the
board and standard everywhere else, so both ends run one well-specified
algorithm with no hand-written table to get wrong. Bit corruption is already
handled by the BLE link layer's own CRC; what reaches this layer is whole
missing packets, which the sequence number catches deterministically, and
truncation, which 16 bits detects comfortably.

## Credit-based batching

The sender transmits frames back to back and the receiver returns one
*cumulative* acknowledgement per batch. That is the whole trick:
`writeValueWithResponse` costs a round trip per 20 bytes, which the upload
path cannot afford, while `writeValueWithoutResponse` alone has no feedback at
all. Batching amortises one round trip over `ACK_EVERY` frames.

Credit is denominated in **bytes, not frames**, because the thing that actually
overflows is the board's UART receive buffer. Initial credit is 512 bytes; the
board grants 2048, half its 4KB buffer, so a full window in flight cannot
overrun it.

The board acknowledges once per drain of its receive buffer, not per frame and
not at a fixed count. Whatever arrived together is one batch. A fixed count
would strand an upload shorter than `ACK_EVERY` waiting for a frame that never
comes.

## Pacing

Credit bounds what the **board** buffers. It says nothing about the HM-10 in
between, which forwards to the board over a 9600 baud UART and has a small
buffer of its own, so writes have to be paced as well. Pacing was a constant
(40 ms per 20-byte chunk) until a sweep showed why that cannot be right.

### The floor is arithmetic

One chunk takes `20 / 960 = 20.83 ms` to leave the module. Pace faster than
that and bytes are offered faster than they can go, so overflow is certain
given enough of them. `MIN_CHUNK_DELAY_MS` is therefore 21, derived rather than
chosen, and the controller cannot go below it.

The measured sweep sits exactly on that boundary, which is the useful part:

| delay | goodput | wire overhead | retransmits | vs floor |
|---|---|---|---|---|
| 40 ms | 249 B/s | 1.40x | 0 | above |
| 30 ms | 307 B/s | 1.46x | 2 | above |
| 25 ms | 269 B/s | 1.96x | 5 | above, strained |
| 20 ms | 93 B/s | 7.15x | 31 | **below** |

Below the floor it is not slow degradation, it is collapse: a seventh of the
goodput at seven times the wire traffic. Integrity held at 8/8 throughout,
because go-back-N kept repairing it, which is the protocol working and also
what hid the problem.

### The controller

`AdaptivePacer` does additive decrease, multiplicative increase, on the delay:

* an acknowledgement that **moves the window** is evidence the link is coping.
  Two in a row and the delay drops 2 ms. A repeat of an ACK we already had
  proves nothing and is ignored;
* a NAK, a damaged frame, or a timeout multiplies the delay by 1.3.

Backing off hard and probing back gently is the right asymmetry: too fast
costs a collapse, too slow costs a few percent.

It starts at 40 ms, well clear of the floor, because the first upload should be
safe rather than fast. State lives on the **connection**, not the upload, so a
second upload starts from what the link already taught us.

Unlike the frame format, the two implementations do not have to agree here:
pacing is local policy, and the receiver neither knows nor cares. They are kept
identical anyway so the benchmark measures what the website will do.

## Sequence verification, go-back-N

The receiver tracks the next sequence it expects.

* In order: accept, advance.
* Gap or bad checksum: NAK with the sequence still wanted, and **discard
  everything after it**, even frames that arrive intact. Accepting them would
  leave a hole in the middle of the program.
* From before the window: a duplicate, because our ACK went missing. Harmless;
  re-acknowledge.

The sender rewinds to the NAK'd sequence and resends. A duplicate NAK for a gap
already being resent does not rewind twice. If neither an ACK nor a NAK arrives
within the timeout, the sender resends from the window base, which is what stops
a lost ACK stalling the upload; after `MAX_RETRANSMITS` it surfaces a real error
rather than looping.

## End-to-end verification

Independent of the frame layer, and the part that actually answers "the board
is unaware it is running nonsense":

1. `B` declares the line count and a CRC-32 of the normalised program.
2. The board accumulates its own CRC over exactly the bytes it writes to
   `program.py`, not over what it believes it received.
3. `E` carries the CRC again. The board compares both totals and replies with
   an `uploaded` verdict.
4. The website's `sendCode` **rejects** unless the verdict matches, and
   `runCode` refuses if no upload has verified.
5. The board independently refuses `start_program` after an upload that did not
   verify, so a client that ignores the verdict still cannot run garbage.

Both ends run the same `normalise_program`, which collapses line endings to
`\n` and guarantees exactly one trailing newline. Nothing else changes: blank
lines and trailing whitespace are preserved, so the stored program is a
faithful copy of what was written. The old protocol dropped blank lines because
an empty line was indistinguishable from noise on the UART; a frame states its
payload length, so an empty line is now explicit.

## Retransmission, precisely

Yes, loss is repaired, but the unit of repair is a **frame**, not a chunk. The
sender has no idea a 20-byte BLE write went missing; the receiver notices that
a frame is damaged or that a sequence number is missing.

What happens to a corrupted or dropped chunk:

1. The chunk was part of a frame. Losing it either truncates that frame or
   makes its checksum fail, so the frame is discarded and counted as damage.
2. The receiver is now missing a sequence number, so it NAKs with the sequence
   it still wants and stops accepting.
3. The sender rewinds to that sequence and resends **that frame and every frame
   after it**, which is go-back-N. Frames already sent past the gap are resent
   even though they arrived intact, because accepting them would leave a hole
   in the middle of the program.
4. If the NAK itself is lost, the sender's timeout fires and it resends from
   the oldest unacknowledged frame, which reaches the same place.
5. After `MAX_RETRANSMITS` the upload fails loudly instead of looping.

Go-back-N rather than selective repeat because the window here is small (2048
bytes, roughly twenty frames) and the receiver writes straight to a file as
frames arrive, so it has nowhere to hold out-of-order frames. Resending a few
extra frames is cheaper than buffering the program twice on a device with
264KB of RAM.

Measured on hardware over BLE: the `typical` and `command_injection` corpora
each took 2 NAKs and recovered byte-exact, so this path runs in practice rather
than only in tests.

## Why the command strings were not the problem

Worth stating plainly, because it is the obvious first instinct: there is no
better choice of magic string.

`x01FIRMCHECK` and friends are guessable, but obscurity is not the issue.
*Any* in-band sentinel is a string a user can type into the Python editor, and
the editor is free-form. Renaming them to something unguessable would reduce
the odds of an accident while leaving the mechanism intact, and a mechanism that
fails only rarely is worse than one that fails visibly.

The fix is structural, and it is threefold:

1. **A kind field.** Control and data are separated by frame structure, not by
   payload content, so a data frame is never scanned for commands.
2. **Length prefixing.** The payload is read by length, so it is never scanned
   for a terminator or sentinel either.
3. **Commands by name in `X` frames.** A framed command carries a name from a
   fixed list, in a frame whose kind says it is a command. User code cannot
   produce one, because user code only ever becomes `D` and `C` frames.

The old strings are gone entirely. Firmware 2.0.0 has no unframed path: a bare
line is ignored, whatever it says, so there is nothing left to injure. Commands
are the names in `COMMAND_NAMES`, carried in `X` frames, and program text only
ever becomes `D` or `C` frames.

There is deliberately no compatibility path. The website checks the handshake
and refuses to upload to anything below 2.0.0, telling the user to update.
Keeping a fallback would have meant keeping the code that corrupted programs,
and a client that silently downgrades to it is the worst of both.

```bash
./tools/run-tests                      # firmware logic, no hardware
```


## MicroPython gotchas

Three divergences from CPython that the shared code has to work around. All
three were found by running on the board, not by reading:

* `int()` will not accept a `bytes` or `bytearray` slice, so header fields are
  parsed by a hand-rolled `_parse_hex`.
* `bytearray` does not support item deletion, so the receive buffer advances by
  slice reassignment rather than `del buffer[:n]`.
* `sys.stdout` translates a lone newline to CRLF, which inserts a byte inside a
  frame and breaks its length. Frames go out via `sys.stdout.buffer`.
